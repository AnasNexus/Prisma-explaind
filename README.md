## What Is Prisma?

Prisma is an ORM (Object-Relational Mapper) for Node.js and TypeScript applications.

It lets you interact with a database using JavaScript objects and methods instead of writing SQL for every operation.

### Why use Prisma?

- **Type-safe database queries:** Helps prevent invalid queries.
- **Prisma Schema:** Defines models and relationships in one place.
- **Migrations:** Tracks database structure changes.
- **Prisma Client:** Provides methods for reading and changing data.
- **Relations:** Makes it easier to work with related records.
- **Developer experience:** Offers a clear and consistent database API.

> Prisma does not replace SQL knowledge. Understanding tables, primary keys, foreign keys, indexes, and relationships is still important.

## Project Requirements

- Node.js
- npm
- Express.js
- Prisma 7
- MariaDB or MySQL
- JavaScript with CommonJS modules

The examples use MariaDB. Prisma's MySQL connector is also used for MySQL databases.

## Installation

Install the application dependencies:

```bash
npm install express @prisma/client@7 @prisma/adapter-mariadb@7 mariadb dotenv
```

Install the Prisma 7 CLI:

```bash
npm install -D @prisma/prisma7@7
```

This project uses the `prisma7` CLI command. Do not mix it with a different Prisma CLI version.

## Initialize Prisma

Initialize a MySQL datasource:

```bash
npx prisma7 init --datasource-provider mysql
```

This creates the Prisma configuration and schema files required by the installed Prisma 7 setup.

## Environment Variables

Create a `.env` file in the project root:

```env
PORT=3000

DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PASS=
DB_NAME=Prisma-Test

DATABASE_URL="mysql://root:@localhost:3306/Prisma-Test"
```

Update the credentials and database name to match your local database.

### What are these variables used for?

| Variable | Purpose |
|---|---|
| `PORT` | Express server port |
| `DB_HOST` | Database host used by the MariaDB adapter |
| `DB_PORT` | Database port |
| `DB_USER` | Database username |
| `DB_PASS` | Database password |
| `DB_NAME` | Database name |
| `DATABASE_URL` | Connection URL used by Prisma CLI tools |

Keep the adapter variables and `DATABASE_URL` pointed at the same database.

Never commit `.env` to Git.

## Prisma Configuration

Prisma 7 uses a configuration file for CLI configuration. A typical `prisma.config.ts` file looks like this:

```ts
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: env("DATABASE_URL"),
  },
});
```

This is a Prisma configuration file, not application TypeScript code. Your Express application and routes can remain JavaScript/CommonJS.

The exact generated configuration may differ depending on the Prisma 7 CLI package and version installed in your project. Keep the configuration generated by your installed CLI unless you have a reason to change it.

## Prisma Schema

The schema file is usually located at:

```text
prisma/schema.prisma
```

Example:

```prisma
generator client {
  provider            = "prisma-client"
  output              = "../src/generated/prisma"
  moduleFormat        = "cjs"
  importFileExtension = "ts"
}

datasource db {
  provider = "mysql"
}

model User {
  id        String   @id @default(uuid())
  email     String   @unique
  name      String?
  createdAt DateTime @default(now())
}
```

### Model fields

| Definition | Meaning |
|---|---|
| `String` | String value |
| `Int` | Integer |
| `Float` | Floating-point number |
| `Boolean` | True or false |
| `DateTime` | Date and time |
| `String?` | Optional string |
| `@id` | Primary key |
| `@unique` | Unique value |
| `@default(uuid())` | Generates a UUID |
| `@default(now())` | Uses the current date and time |

A primary key is already unique, so adding `@unique` to a field that has `@id` is unnecessary.

### Example with more fields

```prisma
model Product {
  id          String   @id @default(uuid())
  name        String
  description String?
  price       Float
  stock       Int      @default(0)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}
```

## Migrations and Client Generation

After creating or changing models, validate the schema:

```bash
npx prisma7 validate
```

Create and apply a migration:

```bash
npx prisma7 migrate dev --name init
```

Generate Prisma Client:

```bash
npx prisma7 generate
```

Whenever you change your schema, create a migration and regenerate the client as required by your setup.

## Connect Prisma to Express

Create a database module, for example:

```text
src/
  config/
    db.js
  generated/
    prisma/
  routes/
    users.js
  server.js
```

### `src/config/db.js`

The import path must match the `output` path in `schema.prisma` and the generated files in your project.

```js
const { PrismaClient } = require("../generated/prisma/client");
const { PrismaMariaDb } = require("@prisma/adapter-mariadb");

const adapter = new PrismaMariaDb({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT),
  user: process.env.DB_USER,
  password: process.env.DB_PASS,
  database: process.env.DB_NAME,
});

const prisma = new PrismaClient({
  adapter,
  log:
    process.env.NODE_ENV === "development"
      ? ["error", "warn", "query"]
      : ["error"],
});

const connectDB = async () => {
  try {
    await prisma.$connect();
    console.log("Database connected successfully.");
  } catch (error) {
    console.error("Database connection failed:", error);
    throw error;
  }
};

const disconnectDB = async () => {
  await prisma.$disconnect();
};

module.exports = {
  prisma,
  connectDB,
  disconnectDB,
};
```

> Important: The generated import path above is an example. Adjust it to match your actual project structure. Also make sure `dotenv` is loaded before this module reads environment variables.

### `src/server.js`

```js
require("dotenv").config();

const express = require("express");
const { connectDB, disconnectDB } = require("./config/db");

const app = express();
const PORT = process.env.PORT || 3000;

app.use(express.json());
app.use(express.urlencoded({ extended: true }));

const startServer = async () => {
  try {
    await connectDB();

    app.listen(PORT, () => {
      console.log(`Server running at http://localhost:${PORT}`);
    });
  } catch (error) {
    console.error("Failed to start server:", error);
    process.exit(1);
  }
};

const shutdown = async () => {
  await disconnectDB();
  process.exit(0);
};

process.on("SIGINT", shutdown);
process.on("SIGTERM", shutdown);

startServer();
```

The database connection is established before the HTTP server starts.

## Basic CRUD Operations

Assume the schema contains a `User` model.

Import the Prisma instance:

```js
const { prisma } = require("../config/db");
```

### 1. Create: `create()`

Create one record:

```js
const user = await prisma.user.create({
  data: {
    email: "user@example.com",
    name: "Alex",
  },
});
```

### 2. Read: `findMany()`

Get all records:

```js
const users = await prisma.user.findMany();
```

### 3. Read one: `findUnique()`

Find a record using a unique field:

```js
const user = await prisma.user.findUnique({
  where: {
    email: "user@example.com",
  },
});
```

### 4. Read first match: `findFirst()`

Find the first record matching a condition:

```js
const user = await prisma.user.findFirst({
  where: {
    name: "Alex",
  },
});
```

### 5. Update: `update()`

Update one record using a unique field:

```js
const user = await prisma.user.update({
  where: {
    email: "user@example.com",
  },
  data: {
    name: "Alex Smith",
  },
});
```

### 6. Update many: `updateMany()`

Update every record matching a condition:

```js
const result = await prisma.user.updateMany({
  where: {
    name: "Alex",
  },
  data: {
    name: "Updated Name",
  },
});

console.log(result.count);
```

### 7. Delete: `delete()`

Delete one record:

```js
const user = await prisma.user.delete({
  where: {
    email: "user@example.com",
  },
});
```

### 8. Delete many: `deleteMany()`

Delete records matching a condition:

```js
const result = await prisma.user.deleteMany({
  where: {
    name: "Temporary User",
  },
});

console.log(result.count);
```

### 9. Create many: `createMany()`

Create multiple records:

```js
const result = await prisma.user.createMany({
  data: [
    { email: "one@example.com", name: "One" },
    { email: "two@example.com", name: "Two" },
  ],
  skipDuplicates: true,
});
```

Support for options such as `skipDuplicates` depends on the database connector.

### 10. Upsert: `upsert()`

Update a record if it exists, otherwise create it:

```js
const user = await prisma.user.upsert({
  where: {
    email: "user@example.com",
  },
  update: {
    name: "Updated Name",
  },
  create: {
    email: "user@example.com",
    name: "New User",
  },
});
```

## Filtering and Conditions

Use `where` to filter records.

### Equality

```js
const users = await prisma.user.findMany({
  where: {
    name: "Alex",
  },
});
```

### Comparison operators

```js
const products = await prisma.product.findMany({
  where: {
    price: {
      gt: 100,
      lte: 500,
    },
  },
});
```

| Operator | Meaning |
|---|---|
| `equals` | Equal to |
| `not` | Not equal to / negation |
| `gt` | Greater than |
| `gte` | Greater than or equal to |
| `lt` | Less than |
| `lte` | Less than or equal to |
| `in` | Matches one of the supplied values |
| `notIn` | Does not match supplied values |

### String filters

```js
const users = await prisma.user.findMany({
  where: {
    email: {
      contains: "@example.com",
    },
  },
});
```

Common string filters include:

- `contains`
- `startsWith`
- `endsWith`
- `equals`

Case sensitivity depends on the database and its collation.

### AND, OR, and NOT

```js
const users = await prisma.user.findMany({
  where: {
    AND: [
      { name: { contains: "Alex" } },
      { email: { endsWith: "@example.com" } },
    ],
  },
});
```

```js
const users = await prisma.user.findMany({
  where: {
    OR: [
      { name: "Alex" },
      { name: "Sam" },
    ],
  },
});
```

```js
const users = await prisma.user.findMany({
  where: {
    NOT: {
      name: "Alex",
    },
  },
});
```

## Sorting and Pagination

### Sorting with `orderBy`

Ascending:

```js
const users = await prisma.user.findMany({
  orderBy: {
    createdAt: "asc",
  },
});
```

Descending:

```js
const users = await prisma.user.findMany({
  orderBy: {
    createdAt: "desc",
  },
});
```

### Limit results with `take`

```js
const users = await prisma.user.findMany({
  take: 10,
});
```

### Skip results with `skip`

```js
const users = await prisma.user.findMany({
  skip: 10,
  take: 10,
});
```

### Example: page-based pagination

```js
const page = 2;
const limit = 10;

const users = await prisma.user.findMany({
  skip: (page - 1) * limit,
  take: limit,
  orderBy: {
    createdAt: "desc",
  },
});
```

## Selecting and Including Fields

### `select`

Return only the fields you need:

```js
const users = await prisma.user.findMany({
  select: {
    id: true,
    name: true,
    email: true,
  },
});
```

Use `select` to avoid returning sensitive or unnecessary fields.

### `include`

Return a record together with related records:

```js
const users = await prisma.user.findMany({
  include: {
    posts: true,
  },
});
```

The `posts` relation must exist in your Prisma schema.

## Relations

Relations connect records from different models.

### One-to-many example

```prisma
model User {
  id    String @id @default(uuid())
  name  String?
  posts Post[]
}

model Post {
  id       String @id @default(uuid())
  title    String
  authorId String
  author   User   @relation(fields: [authorId], references: [id])
}
```

### Create a user with a post

```js
const user = await prisma.user.create({
  data: {
    name: "Alex",
    posts: {
      create: {
        title: "My first post",
      },
    },
  },
});
```

### Connect an existing record

```js
const post = await prisma.post.create({
  data: {
    title: "A connected post",
    author: {
      connect: {
        id: "USER_ID",
      },
    },
  },
});
```

### Disconnect a relation

For optional relations, you can disconnect an existing relation:

```js
await prisma.post.update({
  where: {
    id: "POST_ID",
  },
  data: {
    author: {
      disconnect: true,
    },
  },
});
```

The relation must be optional for this operation to be valid.

### `connectOrCreate`

Connect an existing related record or create it if it does not exist:

```js
const post = await prisma.post.create({
  data: {
    title: "Another post",
    author: {
      connectOrCreate: {
        where: {
          id: "USER_ID",
        },
        create: {
          name: "New Author",
        },
      },
    },
  },
});
```

The `where` field must use a unique field, and the example's relation fields must match your schema.

## Aggregation and Counting

### `count()`

Count records:

```js
const totalUsers = await prisma.user.count();
```

Count records matching a condition:

```js
const total = await prisma.user.count({
  where: {
    name: "Alex",
  },
});
```

### `aggregate()`

Calculate values such as minimum, maximum, average, and sum:

```js
const result = await prisma.product.aggregate({
  _avg: {
    price: true,
  },
  _min: {
    price: true,
  },
  _max: {
    price: true,
  },
  _sum: {
    price: true,
  },
});
```

### `groupBy()`

Group records by a field:

```js
const result = await prisma.product.groupBy({
  by: ["category"],
  _count: {
    id: true,
  },
});
```

The example assumes that `Product` has a `category` field.

## Transactions

Transactions let you execute multiple database operations as one logical unit.

### Sequential transaction

```js
const result = await prisma.$transaction([
  prisma.user.create({
    data: {
      email: "first@example.com",
      name: "First",
    },
  }),
  prisma.user.create({
    data: {
      email: "second@example.com",
      name: "Second",
    },
  }),
]);
```

If an operation in the transaction fails, Prisma rolls back the transaction.

### Interactive transaction

Use an interactive transaction when later operations depend on earlier results:

```js
const result = await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({
    data: {
      email: "transaction@example.com",
      name: "Transaction User",
    },
  });

  return user;
});
```

## Raw Queries

Prisma provides raw SQL methods for cases where the Prisma Client API is not sufficient.

### `$queryRaw`

Use it to retrieve data:

```js
const users = await prisma.$queryRaw`
  SELECT id, email, name
  FROM User
`;
```

### `$executeRaw`

Use it for SQL statements that change data:

```js
const affectedRows = await prisma.$executeRaw`
  UPDATE User
  SET name = ${"Updated Name"}
  WHERE email = ${"user@example.com"}
`;
```

Use tagged-template parameterization as shown. Do not build raw SQL by concatenating untrusted user input.

Raw SQL table and column names must match the actual database schema.

## Error Handling

Always handle errors from asynchronous Prisma operations.

```js
router.get("/users", async (req, res) => {
  try {
    const users = await prisma.user.findMany();

    return res.status(200).json({
      success: true,
      count: users.length,
      users,
    });
  } catch (error) {
    console.error("Failed to fetch users:", error);

    return res.status(500).json({
      success: false,
      message: "Internal server error",
    });
  }
});
```

### Common Prisma error codes

| Code | Meaning |
|---|---|
| `P2002` | Unique constraint violation |
| `P2003` | Foreign key constraint violation |
| `P2025` | Required record was not found |

Example: handle a duplicate email:

```js
try {
  const user = await prisma.user.create({
    data: {
      email: req.body.email,
      name: req.body.name,
    },
  });

  return res.status(201).json({
    success: true,
    user,
  });
} catch (error) {
  if (error.code === "P2002") {
    return res.status(409).json({
      success: false,
      message: "Email already exists",
    });
  }

  return res.status(500).json({
    success: false,
    message: "Internal server error",
  });
}
```

Do not send raw database errors or stack traces to clients in production.

## Best Practices

1. Keep one shared Prisma Client instance for the application.
2. Load environment variables before initializing the database adapter.
3. Do not commit `.env` or database credentials.
4. Validate request data before sending it to Prisma.
5. Use `select` to return only the fields an endpoint needs.
6. Never return password hashes in API responses.
7. Hash passwords with a password-hashing library such as bcrypt before storing them.
8. Use `try/catch` around asynchronous database operations.
9. Use transactions when multiple operations must succeed or fail together.
10. Use migrations to track schema changes.
11. Do not expose raw SQL to user input.
12. Keep Prisma CLI and Prisma packages on compatible versions.
